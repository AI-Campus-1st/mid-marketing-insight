## 데이터

| 날짜 | 결정 | 이유 | 검토한 대안 |
|---|---|---|---|
| Day 1 | DB = SQLite, VectorDB = Chroma | 기획안 권장안. 로컬 파일 하나로 공유·재현 가능 | |
| Day 1 | 뉴스·공시를 `documents` 한 테이블에 저장 (`source_type`으로 구분) | 날짜·기업 기준 조회와 RAG 근거 연결을 한 테이블에서 처리. 기존 초안 구조 유지 | 기획안 5절의 `news` / `disclosures` 분리 |
| Day 1 | 뉴스는 묶음 파일(6,469건) 사용 | 키워드 간 중복이 이미 정리되어 있음 | 키워드별 파일 5개 |
| Day 1 | 뉴스 중복 판단에 원문URL 미사용 | 서로 다른 기사에 같은 URL이 들어간 사례 23개 확인 | URL 기준 |
| Day 1 | 제공 뉴스 수집 기간 = 2023-10-19 ~ 2026-10-19 확인. 결론 예시의 급증 시점을 "2023년 초"에서 "2024년 4월"로 수정 | 2023년 초는 수집 기간 밖. AI 마케팅 기사가 2024-03 48건 → 2024-04 121건으로 급증 후 유지 | |
| Day 1 | 공시 수집 기간 = 2023-10-19 ~ 2026-10-19 | 뉴스와 시점 비교를 위해 기간 정렬 | |
| Day 1 | 앵커 이벤트용 기사를 보강 수집하고 `documents.news_origin`('provided' / 'supplement')으로 구분 | 제공 뉴스가 키워드 기준이라 기업 이벤트 기사가 부족함 (나스미디어 유해광고 필터링 0건, 제일기획 베리에이드 첫 보도 2026-04-07 누락). Q1·Q2 집계에는 'provided'만 써서 왜곡 방지 | 제공 뉴스만 사용 (나스미디어 시차 분석 제외) |
| Day 1 | 보강 기사는 웹 검색으로 직접 확인해 CSV로 정리 (`data/raw/news_supplement/`) | 필요한 기사가 10건 안팎. 네이버 검색 API는 2026-07-31부터 개발자센터 신규 신청이 중단되어 NAVER API HUB(NCP 가입) 필요 | 네이버 검색 API 자동 수집 |
| Day 1 | `ai_events` 테이블 추가 (앵커 이벤트 + 첫 공시 반영 + 반영 시차) | A(뉴스 날짜)와 B(첫 공시)의 작업이 만나는 지점. 결론 문장과 평균 반영 시차 지표의 재료 | |
| Day 1 | `news_company` 테이블 추가 (기사 ↔ 기업, 제목 등장 여부) | 기업별 기사 필터와 앵커 이벤트 탐색에 사용. 제공 뉴스 5개사 언급: 인크로스 93, 제일기획 85, 이노션 45, 플레이디 26, 나스미디어 20건 | |
